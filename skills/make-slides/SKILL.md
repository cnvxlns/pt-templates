# 발표자료 만들기 (pt-templates)

템플릿은 GitHub `cnvxlns/pt-templates` 레포에 폴더 단위로 있다 (예: `vialab/`).
각 폴더는 독립된 React + TypeScript 프로젝트이고, 폴더 안의 `TEMPLATE.md` 가 그 템플릿의 사용법이다.
이 스킬은 모든 템플릿에 공통인 절차만 다룬다. **템플릿별 규칙은 항상 그 폴더의 `TEMPLATE.md` 를 따른다.**

두 곳을 나눠 쓴다.

| | 무엇 | 어디 |
|---|---|---|
| 템플릿 | 공통 컴포넌트 · 빌드 도구 (`node_modules`) | pt-templates git 작업 사본 (1단계) |
| 덱 폴더 | 이 발표의 덱 파일 · 그림 · 빌드 결과 · 스크린샷 · PDF | 발표 자료 폴더 안 `deck/` (3단계) |

**템플릿 작업 사본에는 발표 내용을 쓰지 않는다.** 명령은 템플릿 폴더에서 실행하고,
환경변수 `DECK_DIR=<덱 폴더>` 로 덱 폴더를 가리킨다 (모든 템플릿 공통).

## 1. 템플릿 작업 사본 찾기

플러그인 설치본(`${CLAUDE_PLUGIN_ROOT}`)은 업데이트 때 덮어써지고 `node_modules` 도 없으므로 쓰지 않는다.
사용자의 git 작업 사본을 아래 순서로 찾는다.

1. 환경변수 `PT_TEMPLATES_DIR` 가 있으면 그 경로.
2. 없으면 홈 아래에서 찾는다: `find ~ -maxdepth 5 -type d -name pt-templates -not -path '*/node_modules/*' -not -path '*/.claude/*' 2>/dev/null`
   후보 중 `git -C <경로> remote get-url origin` 이 `cnvxlns/pt-templates` 를 가리키는 것.
3. 그래도 없으면 `git clone https://github.com/cnvxlns/pt-templates.git ~/pt-templates`.

찾은 뒤 작업 트리가 깨끗하면 `git -C <경로> pull --ff-only` 로 최신 템플릿을 받는다.
변경 사항이 있으면 pull 하지 않고 그대로 쓴다 (사용자의 작업을 건드리지 않는다).

## 2. 템플릿 고르기

작업 사본의 `*/TEMPLATE.md` 를 모두 찾아 각 파일 frontmatter 의 `name` · `description` 을 읽는다.

- 사용자가 템플릿을 지정했으면 그것.
- 기존 덱을 고치는 경우, 그 덱이 쓰는 템플릿 (덱 폴더 `README.md` 나 `tsconfig.json` 의 경로로 알 수 있다).
- 요청 내용(소속, 행사 성격, 톤)에 맞는 것이 하나면 그것.
- 둘 이상이 맞거나 판단이 안 서면 후보를 한 줄씩 보여주고 묻는다.

고른 템플릿의 `TEMPLATE.md` 를 **처음부터 끝까지** 읽는다. 쓸 수 있는 컴포넌트, 디자인 규칙,
`DECK_DIR` 사용법, 검사 명령이 거기 있다. 의존성이 없으면(`node_modules` 없음) 그 폴더에서 `npm install`.

## 3. 덱 폴더 정하기

위에서부터 처음 맞는 것을 쓴다.

1. 사용자가 위치를 지정했으면 그곳.
2. 기존 덱을 고치면 그 덱 파일이 있는 폴더.
3. 재료 파일을 받았으면 그 파일이 있는 폴더 안의 `deck/`.
   재료가 여러 폴더에 흩어져 있으면 후보를 보여주고 묻는다.
4. 재료가 없거나 대화로만 받았으면 어디에 둘지 묻는다.

- 덱 폴더는 템플릿 작업 사본 **밖**이어야 한다. 작업 사본 안을 가리키면 다른 위치를 묻는다.
- 정한 폴더가 다른 git 저장소 안이면(`git -C <폴더> rev-parse` 성공) 그 저장소에 덱·`dist/`·`.deck-check/` 가 생긴다.
  만들기 전에 그래도 되는지 묻는다.
- 기존 덱이 작업 사본의 비공개 폴더(예: `vialab/src/decks/private/`)에 있으면 그 자리에서 고치되,
  레포 밖으로 옮길지 한 줄로 제안한다.

덱 폴더가 새로 생겼으면 `README.md` 를 하나 둔다: 쓰는 템플릿 경로, `DECK_DIR` 를 붙인 dev·build·check 명령, 덱 목록.

## 4. 내용 정리

- 재료: 사용자가 준 파일(원고 md, 보고서, 노트, 이전 덱), 대화 내용. 파일 경로를 받았으면 전부 읽는다.
- **숫자·사실을 만들어내지 않는다.** 재료에 없는 값은 비워 두거나 `TODO` 로 표시하고 마지막에 알린다.
  발표자·날짜처럼 사소한 빈칸은 자리표시자로 채우고 알린다.
- 슬라이드 한 장에 메시지 하나. 화면에는 요점만 두고, 말로 할 설명은 발표자 노트(`notes`)로 보낸다.
- 쓰기 전에 슬라이드 목록(장마다 label + 레이아웃)을 먼저 정한다. 사용자가 목차 검토를 원했을 때만 멈춰서 보여준다.

## 5. 작성

`TEMPLATE.md` 의 방법대로 덱 파일을 덱 폴더에 만든다. 템플릿의 컴포넌트를 쓰고, 색·크기를 직접 하드코딩하지 않는다.
그림·영상도 덱 폴더에 둔다.

**템플릿은 공개 레포다.** 사용자의 발표 내용(내부 수치, 장비 시리얼·IP, 미결 사항 등)은
템플릿 작업 사본에 절대 넣지 않는다 (git 제외 폴더라도 3단계의 예외가 아니면 쓰지 않는다).

## 6. 검사

템플릿 폴더에서 `DECK_DIR=<덱 폴더>` 를 붙여 `TEMPLATE.md` 의 타입체크·검사 명령(스크린샷 포함)을 돌린다.
결과물은 덱 폴더에 생긴다.

- 넘침·잘림 보고가 없어질 때까지 고친다. 내용을 줄이거나, 장을 나누거나, 더 촘촘한 변형(`compact`, `size="sm"` 등)을 쓴다.
- 스크린샷을 직접 본다. 보고된 장은 반드시, 나머지도 훑는다 (10장 이하면 전부). 검사기가 못 잡는 것:
  너무 빈 장, 한쪽으로 쏠린 배치, 줄바꿈이 어색한 제목, 읽기 힘든 작은 글자.

## 7. 전달

- 덱 파일 경로, 보는 방법(`DECK_DIR` 를 붙인 개발 서버 명령과 주소 — 사용자가 원하면 백그라운드로 띄워 준다), 만든 경우 PDF 경로.
- 재료에 없어 비워 둔 것, 자리표시자, 판단이 필요한 부분.
- 덱 폴더는 템플릿 레포의 커밋 대상이 아니다. 템플릿·컴포넌트를 고쳤다면 무엇을 바꿨는지 알리고,
  커밋·푸시는 사용자가 요청할 때만 한다.

## 템플릿에 없는 것이 필요할 때

필요한 표현이 기존 컴포넌트로 안 되면, 그 템플릿의 컴포넌트로 새로 만들고
`TEMPLATE.md` 가 정한 방법대로 카탈로그에도 등록한다. 컴포넌트는 템플릿 작업 사본에 만든다 (공통 코드이므로).
카탈로그 예제에는 일반적인 예시 내용만 쓴다 (공개 레포).
